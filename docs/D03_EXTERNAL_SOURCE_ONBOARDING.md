# D03 external source onboarding

Status: infrastructure contract. No external dataset is approved merely because it appears in this document or registry.

## Boundary

`corpus_v01` does not download network data. External training data must first be reviewed and materialized as a local UTF-8 JSONL artifact. The registry then binds that exact artifact by SHA-256.

A registry approval is project evidence, not an independent legal opinion. License terms, privacy obligations, attribution, redistribution conditions and dataset-specific restrictions still need source-by-source review before `training_eligible` is set to `true`.

## Required source contract

Each external registry entry records:

- stable `source_id` and `source_version`;
- one corpus `stratum`: `uk`, `en` or `code`;
- explicit boolean `training_eligible`;
- `license.identifier` and `license.review_status=approved`;
- provenance with `external_source=true`, `benchmark_material=false` and a source URL;
- rights review with `training_use=allowed`, `review_status=approved` and `reviewed_by`;
- local JSONL materialization path and exact lowercase SHA-256;
- JSONL text and document-id field names.

The local artifact must remain inside the repository root. Symlink/path traversal escapes are rejected. A changed byte changes the hash and blocks ingestion.

## Materialized JSONL

Each non-empty line is an object containing a stable document identifier and string text, for example:

```json
{"document_id":"doc-000001","text":"..."}
```

Document IDs must be unique inside a source artifact. Corpus record IDs are derived deterministically from source ID, source version, document ID and raw text.

## Capability-corpus rule

Project-authored synthetic records are a mechanics fallback only. Once at least one source is explicitly training-eligible, `corpus_v01` builds from eligible external materializations and does not silently fill missing token targets with project-authored synthetic text. If the external materializations do not satisfy all UK/EN/code target budgets after normalization, quality filtering, exact deduplication and reserved-evaluation removal, the build fails closed.

This behavior is deliberate: a target byte/token count must not be interpreted as evidence of a real capability corpus when most of those bytes were generated by the project fixture generator.

## Onboarding sequence

1. Select a candidate dataset and freeze its exact source/version.
2. Review license/terms, training permission, privacy obligations, benchmark overlap risk and required attribution.
3. Materialize only the approved subset into UTF-8 JSONL outside the corpus builder.
4. Compute SHA-256 of the exact materialized file.
5. Add the registry entry with `training_eligible=false` while review evidence is incomplete.
6. Set `training_eligible=true` only after the explicit license/rights/provenance contract is complete.
7. Recompute the external registry identity SHA-256.
8. Rebuild twice and require identical corpus/shard identities.
9. Inspect per-source/per-stratum counts, reserved-evaluation removals and the manifest truth boundary.
10. Only then can a capability-training launch request reference that corpus identity.
